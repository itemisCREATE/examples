Embedded Sub Machines

This example demonstrates embedded sub machines: a state machine that a state of another state machine owns, enters, runs and exits. It is the counterpart of the Multi State Machines example, which uses the same import mechanism but keeps every machine's life cycle in the hands of the client.

For more details, please also refer to the Multi state machine modeling section of the user guide.

Declaring a Sub Machine

A state machine becomes embeddable by annotating it with @SubMachine. In this example the dimmer machine carries that annotation:

@SubMachine

The annotation changes what is generated for it: an embedded sub machine has no run cycle of its own. It is never stepped by a client and never by a timer - only by the owner it is embedded in.

Embedding it in a State

The owner imports the machine and declares a variable of that type, exactly as for any other imported state machine:

import: "dimmer.ysc"
var ceiling : dimmer

What makes it embedded is the submachine keyword in a state's specification. The On state of the lamp machine embeds two dimmers:

submachine ceiling
submachine reading

What the Owner Takes Over

Embedding hands three responsibilities to the owning state:

  • Life cycle. Entering the state enters the sub machine, leaving it exits the sub machine. Nobody calls enter or exit on it. Exiting the owner exits every sub machine it has active.
  • Execution. The sub machine runs inside the owner's run-to-completion step. There is no separate cycle to schedule and no ordering to get right between the two.
  • Multiplicity. A state may embed several sub machines, as On does here. All of them are entered, cycled and exited together.

Talking to a Sub Machine

A sub machine keeps its own interface, and the variable that holds it is how the owner reaches it. The On state forwards the lamp's brighten event to both dimmers:

brighten /
raise ceiling.step;
raise reading.step

The other direction works as well: a sub machine's out events and variables are visible to the owner. Here the ceiling dimmer raises maxReached when it reaches full brightness, and the lamp treats that as a reason to switch off - the transition leaving On triggers on either the client's toggle or the sub machine's event:

toggle,
ceiling.maxReached

Raising an event on a sub machine also drives the owner: the raise starts the owner's run-to-completion step, and the sub machine is stepped as part of it. If the embedding state is not active the step still happens, but the sub machine is not running and does not consume the event.

The Example Model

lamp is the owner. It is Off until toggle switches it On, and the On state embeds the two dimmer sub machines ceiling and reading.

dimmer is the sub machine. It alternates between Dim and Bright on every step event, reports its level in the brightness variable and raises maxReached when it reaches the top. Switching the lamp off exits both dimmers; switching it on again starts them from their entry state.

Simulating Embedded Sub Machines

Simulate the owner, in this example the lamp machine. Its sub machines are simulated with it and can be selected in the simulation view - they become active when On is entered and inactive again when it is left.
