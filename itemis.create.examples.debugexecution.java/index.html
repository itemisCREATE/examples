Execution Logging with @DebugExecution

@DebugExecution is a statechart annotation. Where it is present, the generator emits a log call for every expression the state machine evaluates: each assignment, each guard and each time event is reported with the source text it came from, with the value of every variable it read, and with the value it produced. It is print debugging for a statechart, without adding a single action to the model.

For more details on the generator model this example uses, please also refer to the Java code generator section of the user guide.

Nothing about the generator model changes, and removing the annotation removes the calls again — the logging is generated, not switched on at run time. That also means it costs nothing in a build that does not carry the annotation.

The statechart

A light switch that brightens by one step per press and dims itself again after a while. Each part of it is there to produce one kind of log entry: 

@EventDriven

// Report every expression the statechart evaluates.
@DebugExecution

interface:
	in event on_button
	in event off_button

	var brightness : integer = 0
	var step : integer = 1
	var maxBrightness : integer = 3
	var timeout : integer = 30

	out event on
	out event off

  • A guarded transition leaves Off: on_button [brightness < maxBrightness] / brightness = brightness + step. A guard is reported with its own source, whether it held (: true or : false), and the value of each variable it read.
  • An assignment that reads other variables is its effect. Every variable read is reported before the write, the result after it.
  • A guarded local reaction in On brightens on every further press: on_button [brightness < maxBrightness] / brightness = brightness + step. Its guard is reported exactly like a transition's; at full brightness it reports : false and nothing else happens.
  • A time event scheduled from a variable leaves On: off_button, after timeout s / brightness = 0. The trigger is reported together with the value the timer was actually scheduled with, in the unit the statechart wrote. It shares the transition with off_button, and the time event is reported only when it was the timer that fired — switching off by hand logs the assignment alone.

The last one is worth spelling out: timeout is handed to the timer service in milliseconds, and what the log reports is the value converted back into seconds. That is the number to check when a timer fires at the wrong moment.

The generated logger

The generator writes an itemis.create.core.Logger next to the machine and gives the machine a setDebugLog(). The application decides where the entries go: the default logger prints to the console, and the constructor taking a List also appends every entry to it, which is how a test reads back what the machine reported.

Running it

Run Main with Run As → Java Application, or from the command line: 

javac -d bin $(find src src-gen -name "*.java")
java -cp bin itemis.create.examples.debugexecution.Main

Entering the machine runs the entry action of Off. The first press takes the guarded transition into On, the second is handled by the local reaction, and a press at full brightness only reports the guard that failed. Typing off leaves On by hand, so the entry action of Off runs again: 

brightness = 0
  < brightness = 0

Press enter to push the button, type 'off' to switch off, 'quit' to leave.

@DebugExecution or generic tracing?

They answer different questions. @DebugExecution shows the expressions, as written in the statechart, in the order they were evaluated; it is meant to be read by a person who is debugging a model. Generic tracing (see the Generic Tracing examples) reports the state machine's behaviour — states, transitions, events, variable writes, time events — as typed events that a program can react to. Both can be switched on at the same time.
